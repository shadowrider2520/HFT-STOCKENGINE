Why it is built this way

Three data structures doing the work

Each one is chosen for a specific question the matcher asks on every order. The result is expected O(log N) price discovery with O(1) time priority.

01

Treap price ladder

A BST on price and a max-heap on a random priority at the same time. Insert, delete and find the best price stay expected O(log N) even when prices arrive strictly ascending — the exact input that turns a plain BST into a linked list.

O(log N) insertO(log N) best price
02

Circular queue per level

Time priority is strict FIFO, so each price level owns a ring buffer. The head advances on a fill instead of shifting the array, giving O(1) enqueue, dequeue and peek with no allocation on the hot path.

FIFOO(1) enqueue
03

Price-time matching

Best price first, earliest arrival first inside a price. Aggressors sweep as many levels as needed, print at the resting order's price, and leave any remainder at the front of its queue.

partial fillsmulti-level sweep
04

Live structural event log

NODE_INSERT, rotations, enqueues, dequeues, trades and rejections are recorded in a 5,000-event ring buffer and streamed to the terminal, so the tree you see is the tree the engine is using.

/api/events500 ms poll
05

Reproducible benchmarks

A seeded simulator runs one million orders in random or sequential mode, reports throughput, trades and both ladder heights, and compares the Treap against an unbalanced baseline.

seeded1M orders
06

Persistence and history

Trades are appended to CSV, reloaded on boot, and folded into candles and per-trader positions. A seeder fills an empty store so charts are never blank on first open.

CSV append-onlyrestart-safe
The path of one order

Gateway in, matched trade out

One synchronized entry point mutates engine state, so the web thread pool can poll books and charts while orders are matched without seeing a half-updated book.

Step 1

OrderGateway

Parses trader,ticker,side,price,qty or JSON, validates every field, and stamps the arrival time used for time priority.

→
Step 2

MatchingController

Picks the symbol's book, inserts the order, then matches while best bid ≥ best ask. This is the only mutating entry point.

→
Step 3

OrderBook

Two Treaps per symbol: bids searched from the right, asks from the left. The crossing test is two O(log N) lookups and one compare.

→
Step 4

Trade tape + event log

Executions land on a capped 10k tape and in CSV; structural changes stream to the UI timeline and the SVG tree view.

The Treap bound is expected, not worst case. That is the deliberate trade: no height field, no colour field, one rotation per level, and a vanishingly small chance of a pathological draw.

What you can do in the terminal

  • Submit a limit order and watch it rest, cross, or sweep several levels.
  • Run a simulation of up to one million seeded orders and read the throughput.
  • Inspect both ladders as live SVG trees with per-node order counts.
  • Filter the event timeline by structure operation to isolate rotations or fills.
  • Follow the depth and candles for the selected symbol, refreshed every second.
